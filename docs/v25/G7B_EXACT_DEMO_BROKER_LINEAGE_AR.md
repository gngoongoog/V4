# BRAINTRADE V25 — G7-B | إسناد قرار Adaptive إلى صفقة MT5 Demo مكتملة (بحث فقط)

## الفرق عن G7-A

G7-A يحفظ قراري **Frozen وAdaptive** متزامنين مع شمعة M1 مكتملة وبصمة محلية ولا يرسل أي أوامر. مرحلة G7-B تضيف أداة `scripts/g7_demo_broker_lineage.py` **للقراءة فقط** تفحص ما إذا كان قرار Adaptive نفسه أنتج أمراً حقيقياً في سجل Core، ثم هل يوجد دليل إغلاق Broker مكتمل، بدلاً من احتساب كل إشارة على أنها صفقة.

لا توجد أوامر MT5 إضافية ولا تعديل لقرار الدخول أو اللوت أو المخاطر أو بيانات التدريب.

## سلسلة الربط الصارمة

1. فحص مصدر دراسة G7-A بالكامل بواسطة `g7_core_source_audit.check` أولاً: لا تُقبل سجلات تم تعديلها أو فقدت بصمتها.
2. مطابقة `frozen_coordinator_decisions.adaptive` **ككائن JSON كامل** مع `broker_commands.payload.signal`، وبوقت `created_ms == observed_ms`، وسياق الخادم/الحساب/الرمز/العملة، وهوية `system`، والوضع الموافق، وهدف التنفيذ `demo`. التشابه بالسعر أو الاتجاه لا يكفي.
3. قراءة `broker_commands.result.deal` الأصلي ثم ربط `coordinator_broker_samples.payload.open_command_id` بنفس الأمر، والتحقق من `position_id` و`open_deal` و`closed_ms` وهوية المود.
4. شرط وجود سجل `coordinator_broker_admissions` الأصلي الذي كُتب مع أول قبول للسجل، وبصمة SHA-256 غير معدلة وتاريخ قبول `admitted_ms >= closed_ms`.
5. **إعادة احتساب** رسوم ونتائج بروكر MT5 من كل `broker_deals` الخاصة بالمركز، بإعادة استخدام فحوص G6-B التي تحسب `profit + commission + swap + fee` وترفض انعكاسات Netting الغامضة، إغلاق الحجم الجزئي، والرسوم المفقودة. يشترط تطابق نتيجة التدريب مع هذه الدفاتر.
6. لا يُحتسب مركز مرتين عند وجود نسبتين من دراستين لنفس `context + position_id`. كل حالات التعارض والنتائج غير المكتملة تُعرض كأسباب استبعاد صريحة.

## كيف تشغل التدقيق؟

على نسخة من مشروع GitHub، وبوجود SQLite **الأصلية** لبرنامج Core:

```powershell
python scripts/g7_demo_broker_lineage.py --db "C:\path\to\actual\Core.sqlite" --output "g7-b-report.json"
```

بدّل المسار باسم قاعدة Core الحقيقي؛ لا تفترض أن هذا المثال هو مكان قاعدة بيانات الجهاز. الأمر لا يفتح تداولاً ولا يطلب بيانات حساب MT5. ترفض الأداة الكتابة فوق تقرير موجود وتفتح SQLite بوضع `mode=ro`.

يمكن إجراء الاختبارات دون وسيط أو سوق مفتوح:

```powershell
python -m unittest discover -s tests -p "test_g7_demo_broker_lineage.py" -v
```

## ما الذي تعنيه الأرقام؟

- `paired_decisions`: عدد الأزواج المسجلة مسبقاً، **ليس** عدد صفقات الوسيط.
- `exact_open_intents`: أوامر أصلية من نفس قرار Adaptive، وقد تظل غير منفذة أو غير محسومة.
- `verified_closed_adaptive_positions`: مراكز Demo مغلقة بالكامل وثبت ارتباطها محلياً بكل الأدلة.
- `booked_adaptive_net` و`mean_adaptive_net_r`: وصف للصفقات المغلقة المقبولة **فقط** وليس كل الفرص أو صافي الحساب.
- `unverified_by_reason` و`no_exact_broker_open_intent`: جزء من مقام المراجعة ولا يجوز إخفاؤه أو إعطاؤه ربحاً صفرياً مفترضاً.
- `frozen_broker_pnl=null` و`paired_broker_delta=null`: لا توجد نتيجة Frozen منفذة، فلا يمكن الادعاء أن Adaptive تفوق عليه بمال الوسيط.

## قيد المقارنة

الربط يحفظ **ذراع Adaptive منفّذاً واحداً عند توفر الإغلاق الحقيقي**، أما Frozen فمجرد قرار افتراضي. هذا ليس A/B بين مجموعتين منفذتين، ولا ينقل نتائج ورقية إلى نتائج وسيط. SHA/SQLite تُثبت اتساقاً محلياً فقط، ولا تمنع مسؤول الجهاز من تعديل كل البيانات، ولا تمثل تصديقاً مستقلاً أو معيار جاهزية لحساب REAL.

يظل الوضع `inconclusive` حتى بوجود نتائج محلية صحيحة. مطلوب لاحقاً: رصد العينة الكاملة بما فيها أوامر غير مرتبطة بالمقارنة، وتجميع تقارير تغطية مدققة، ثم دراسة تنفيذ مستقبلية مصممة مسبقاً دون تغيير مخاطرة المستخدم.

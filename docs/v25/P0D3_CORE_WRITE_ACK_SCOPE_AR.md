# BRAINTRADE Enterprise V25 — P0-D3: استجابات الحفظ المتأخرة وعزل حساب MT5

## أصل المشكلة

كانت حواجز `PanelReadFence` و`ScopedReadFence` ترفض **ردود القراءة** المتأخرة، لكن عمليات الكتابة في صفحات Windows كانت تُرسل ثم تعرض نجاح الحفظ على أساس نطاق React القديم بعد `await`. بالتالي يمكن نظرياً أن ينتقل المشغل من Demo A إلى Demo B أو من صفحة Settings إلى Execution قبل عودة طلب حفظ A، فتظهر رسالة نجاح على B أو تُشغّل قراءة جديدة للصفحة الخطأ.

هذا خلل في **إثبات الحالة المعروضة**، وليس دليلاً على أن Rust Core حفظ فعلياً على حساب خاطئ. صلاحية الحفظ ومعايرة Broker ما تزال مسؤولية المحرك.

## الإصلاح البرمجي

- `apps/terminal/src/operator-write-fence.ts` يملك رمزاً لكل طلب كتابة ونطاقه `[page, MT5 context, preview]`. يرفض إرسال كتابتين متداخلتين على مستوى الواجهة بشكل تزامني، قبل أن تحدث إعادة رسم React.
- تغيّر الحساب/الصفحة/المعاينة يبطل الرمز فوراً، بما فيه دورة A→B→A. يظل المنع على كتابة ثانية قائماً **حتى يسوّي IPC نتيجة الطلب الأول**، لأن طلب HTTP/MT5 الذي غادر التطبيق لا يمكن افتراض إلغائه.
- بعد كل `await` حساس تُفحص صلاحية الرمز قبل رسالة النجاح، وقراءة التحقق، وتحديث حالة الصفحة/المخاطر/العقول. إذا أصبح الرمز قديماً، يمتنع النظام عن إظهار نجاح كاذب ويعرض تنبيهاً محايداً: قد يكون Core طبّق التغيير على الجلسة السابقة؛ أعد القراءة.
- حُميت عمليات: المخاطر، المحفظة، الإعدادات وTelegram، التداول وتكاليفه، تفعيل العقول، تغيير المنسق، ربط Demo/REAL، النسخ/التصدير، تشغيل/إلغاء Backtest، START وإعادة الاتصال والخروج الكامل.
- **STOP استثناء مقصود:** طلب وقف الدخول عبر Rust Core يظل متاحاً أثناء انتظار طلب إعدادات ولا ينتظر هذا الطابور. لا يغلق مراكز موجودة، ولا يتجاوز قواعد التنفيذ في Core.
- أعيد تهيئة `EnterpriseSupervisor` ومحرر المنسق وتكاليفه والربط وBacktest ونماذج Micro عند تغيّر نطاق الحساب، كي لا تبقى مسودات حساب سابق داخل حالة React المحلية.

## الاختبارات الآلية

- `apps/terminal/tests/operator-write-fence.test.mjs` ينفذ منطق `OperatorWriteFence` في Node ويعيد تمثيل:
  1. نتيجة حفظ طبيعية يعلن نجاحها مرة واحدة.
  2. طلبان متزامنان: لا يدخل الثاني حتى تسوية الأول.
  3. تبديل حساب A→B→A في منتصف طلب مُعلّق.
  4. فشل متأخر من حساب قديم لا يكتب فوق الحالة الجديدة.
  5. تبديل صفحة أو دخول المعاينة أثناء الحفظ.
  6. محاولة استعمال تذكرة مزوّرة أو إنهاء طلب مختلف.
  7. التحقق من ربط أوامر واجهة React بحاجز الكتابة وكون STOP خارج الطابور.
- فحص Windows/Linux: `npm --prefix apps/terminal test` ثم `npm --prefix apps/terminal run build` ضمن البنية المقفلة، يليهما فحص Windows Portable الكامل عند نجاح CI.

## ما لم يتم إثباته

- هذه الاختبارات **ليست** إلغاء لأوامر وصلت لـRust أو MetaTrader، وليست اختبار نقر WebView2 فعلي.
- عند فقدان اتصال API بعد إرسال POST، النتيجة تكون **غير محسومة** حتى يقرأ Core حالته؛ لا يجوز إعادة إرسال أمر وسيط تلقائياً. `OperatorWriteFence` يغلق ازدواج الكتابة من نفس الواجهة فقط وليس بديلاً عن Broker Journal أو الحماية الدائمة.
- بناء Portable عبر CI لا يثبت نجاح جميع أزرار Windows بالنقر ولا مسار EA OnTick، ولا يسمح باعتماد REAL.
- بوابة G3/Windows وG2/MT5 Demo وMetaEditor Compile تبقى `NOT TESTED` حتى قبولها عملياً.

## الخطوة التالية

بعد قبول اختبارات P0-D3 من CI: توسيع اختبارات واجهة Tauri على Windows الفعلي مع WebView2 للتحقق من 22 صفحة، المودالات، التعامل مع فصل Core، وملء/حفظ الإعدادات بإذن Demo، مع حفظ صورة وتقرير زمن رد لكل زر.

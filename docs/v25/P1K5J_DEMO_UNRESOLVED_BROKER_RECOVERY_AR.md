# BRAINTRADE V4 Enterprise V25 — P1-K5J: تشخيص أوامر Demo العالقة بعد انقطاع الاتصال

هذه مرحلة **تشخيص للقراءة فقط** ضمن تطوير واجهة Windows ومراقبة Core. لا تتصل مباشرة بمنصة MT5 ولا تطلق أو تعيد إطلاق أوامر الوسيط. ترتكز على P1-K5I وتبقى نتائج Frozen Sniper البحثية دون صفقات.

## الخطر المعالج

رسالة انقطاع الاتصال بعد إرسال أمر **لا تبرهن أن الوسيط رفض الأمر**. قد يكون الأمر `dispatched` أو `unknown` أو `placed` أو `partial` أو `filled` من دون اكتمال مزامنته مع Core. إعادة محاولة أمر جديد لمجرد غياب ردّ Gateway قد تتسبب بمركز مضاعف. لذلك لا يُترجم اختفاء الرسالة إلى إذن بتنفيذ أمر ثانٍ.

## التغيير الفعلي

- يبحث Core في سجل SQLite `broker_commands` للـDemo الحالي نفسه، بعد التحقق من `account_trade_mode=0` ومن أرشيف التجميد `SHA-256` وسياق الحساب.
- يعرض عدداً منفصلاً للأوامر غير المرسلة في الطابور `queued`، والأوامر التي خرجت من الطابور ولم تُحسم، وتلك التي بقيت نتيجتها مجهولة، بالإضافة إلى عدد أوامر أخرى عالقة في قاعدة البيانات من دون عرض هويات الحسابات الأخرى.
- يفحص اتساق كل طلب مع `id` و`kind` و`context` و`created_ms`، ويمنع عرض أعداد معتمدة عند فساد السجل أو تجاوز عدد صفوف الفحص.
- **حتى عند وجود صفر أوامر عالقة**، يرجع `new_orders_authorized=false` و`requires_live_broker_reconciliation=true`، لأن SQLite المحلي ليس برهاناً على خلو حساب الوسيط من مراكز أو أوامر.
- الأرشيف يستمر بعد إعادة تشغيل Core ما دامت قاعدة SQLite موجودة؛ ولا يمس هذا الفحص إعدادات إدارة المخاطر أو حرية أحجام الحسابات الصغيرة، ولا يحرر قاطع الخسارة أو يرسل أو يعيد إرسال أوامر.
- صفحة Sniper تعرض تحذيراً مفهوماً بأن حالة `unknown` أو `dispatched` أو `partial` لا تُعد فشلاً آمناً لإعادة الإرسال. لا يجوز تحويل هذه المعلومات تلقائياً إلى صلاحيات التنفيذ.

## حالات الاختبار المصطنعة

1. إدراج `queued + dispatched + unknown + partial` ثم التأكد من تصنيفها ورفض تقرير السماح بإعادة التنفيذ.
2. وجود طلب عالق لحساب Demo آخر، مع عزل بيانات الحساب ومنع تفسيره بأن النظام كله خالٍ من الأوامر.
3. تغيير حمولة أحد أوامر Core المحفوظة، وعندها لا تعرض الواجهة نتيجة مثبتة.
4. إغلاق SQLite وفتحه مع أمر `dispatched` وحيد والتأكد من استمرار حالة عدم الحسم.
5. منع الاستعلام من حساب REAL أو من Telemetry غير متصلة.
6. GitHub Research + Windows Legacy + V25 Portable على Commit واحد؛ اختبارات MT5 الحقيقية تحتاج جلسة تشغيل مراقبة منفصلة.

## حدود الحل

هذا الفحص **لا يكتشف تلقائياً** حالة أمر لم يُحفظ أصلاً في قاعدة Core، ولا يغني عن استرجاع تاريخ Deals والأوامر والمراكز من الوسيط عند عودة الاتصال. وجود `state='observed'` في قاعدة Core ليس شهادة مستقلة من البورصة. كما أنه ليس تغييراً لمحرك إرسال أوامر MT5؛ الحماية التشغيلية تعتمد أيضاً على قواعد الـGateway القديمة وتحتاج اختباراً مباشراً على جهاز Windows.

## ما يلي ضمن قبول V25

إكمال اختبارات إعادة الاتصال الفعلية بالوسيط، ثم اختبار الحالات ذات نتائج التنفيذ غير المعلومة مع التأكد عملياً من عدم وجود محاولات ثانية بالمعرف نفسه أو معرف جديد قبل إعادة بناء حالة الأمر من بيانات MT5، وبعدها فحص MetaEditor وWebView2 والملف التنفيذي على جهاز Windows.

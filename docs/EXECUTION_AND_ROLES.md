# Historical BrainTrade 0.7.0 execution design — superseded by 0.7.1

> **Do not use the old SOLO/veto/target-compensation descriptions below as operating instructions.** In v0.7.1 and its October 21 audit, SOLO broker entries are disabled; the selected-mode `system` coordinator alone submits new MT5 entries. Expert advisor consensus cannot veto Scalping, Swing or Sniper decisions; MT5 journal and Paper observations are separate; fixed Sniper TP is never widened silently. For current details see [brain controls](BRAIN_CONTROL_SNIPER_AR.md) and [the execution integrity audit](AUDIT_2026_10_21_EXECUTION_LEARNING_INTEGRITY.md).

## Historical 0.7.0 background (not current behavior)

The bound Demo MT5 account can receive actual orders when global START is active. Initial startup/restart is STOPPED; execution is initially unbound. The account type is checked against the broker: Demo=0, Live=2. Live must be selected and rebound explicitly while stopped and without unresolved intents or owned positions. Changing accounts never silently transfers ownership.

## Coordinator and independent brains

The Execution page has 17 identities: system, Gann, Wyckoff, trend, momentum, structure, supply/demand zones, broker DOM, activity profile, Gann+DOM+profile, CES, KTE, regime, Liquidity Sweep a manually selected generated strategy, Liquidity Sweep, Trend Pullback, and dedicated Sniper Learner (magic 410617). Each has its own configuration, magic number, signals, broker positions, recorded deals and results. CES/KTE v1 use M1; the other secondary policies can select the available native frames. News and volatility are analysis/context components, not separate execution strategies.

Secondary brains are advisors by default. The SOLO button removes that brain from the actual coordinator vote and enables its own policy to submit orders independently of other brains. It does not press global START. Return disables new independent entries. An outstanding intent or owned position puts the brain in RETURNING: it keeps managing its original position and rejoins the coordinator only after settlement. SL/TP and the recorded maximum holding time remain tied to the entry. STOP prevents new entries; timed exits and broker SL/TP remain active. Full application exit stops client-side timed management; broker-attached stops remain at the broker.

A membership/configuration change cancels queued entries and changes a persisted revision. Dispatched entries must match the revision at final authorization; already submitted orders cannot be undone. All brains use the one master START/STOP. The system identity is always the coordinator, and has no SOLO switch.

## Adaptive coordinator

Expert uses the actual non-SOLO, non-returning member signals. Before 20 scored observations a member's weight is 1. Subsequently the weight is `0.5 + (wins + 10) / (samples + 20)`, bounded to 0.5–1.5. BUY/SELL weights are summed; normalized imbalance at least +0.20 or at most -0.20 selects a direction, otherwise WAIT. Other modes retain their own trigger, vetoed when opposing weight is at least 2 and exceeds supporting weight by more than 0.5. The Execution detail shows participating members, weights, sample counts and reasons.

Adaptive evidence has two causal sources. The preferred source on a bound MT5 Demo account is exact closed coordinator broker evidence: matched MT5 deals are aggregated using broker-reported profit, commission, swap and fee, and the result is assigned only to members that were ready and supported the executed side at entry. This gives the coordinator real Demo feedback rather than Shadow-only simulated PnL. The completed-bar fallback still records one prospective observation per member/frame/bar while START is active and matures it from exactly 12 later completed bars using the frozen entry quote/contract/commission/slippage and positive historical exit spread where available. Missing retained horizons expire; they are never invented. Samples remain isolated by account/server/symbol/currency, mode, brain, frame and generated-report ID and persist in SQLite. Weighting is a smoothed observed win frequency, not calibrated confidence, deep learning or a profitability claim. The older imported ML challenger pipeline remains research-only and has no automatic promotion.

## Order transport and per-brain limits

The Core persists intent before dispatch. The gateway validates exact account, broker contract, owned ticket, quote and terminal permissions, obtains final Core authorization, rechecks the account, then durably journals and commits the command before `order_send`. Regular orders retain broker `order_check`; fast Sniper tick entries and owned fast closes may skip that broker round-trip only after equivalent local geometry/contract checks. Repeated IDs, timeouts, unknown replies and accepted-but-unobserved fills never cause a blind resend. Unknown intents remain blocked until broker reconciliation; broker-modified comments may prevent automatic reconciliation. No top-up is attempted after partial fills. Exit requests use actual remaining owned volume. Netting accounts serialize symbol ownership; separate simultaneous brain positions require a hedging account.

Optional lot/risk/daily loss/drawdown/spread budgets default OFF per brain, as requested. Enabling them applies the selected settings. Drawdown uses the persisted highest observed equity for that account/symbol; deposits/withdrawals are not normalized. One active position/unsettled intent per brain, lot-step validity, ownership, account identity, quote freshness, stop geometry, START and duplicate prevention are execution correctness requirements. Strategy conditions and SL/TP still apply. Generated strategies require a manually selected saved report from the same account, symbol and timeframe; no automatic promotion based on research performance.

## Portfolio-wide exposure management v1

The development line adds a separate portfolio gate over all BrainTrade execution identities. It is **OFF by default**, so upgrading from the verified 0.6 checkpoint does not silently restrict existing execution. When explicitly enabled while STOPPED, it enforces three aggregate entry budgets: maximum exposure slots (visible owned positions plus unresolved open intents), maximum total lots, and maximum estimated stop risk as a percentage of current equity.

The gate is applied after brains have produced their queued entry intents and before the gateway can retrieve those entries. Queued entries are considered in deterministic creation order. An entry that would exceed any aggregate limit is changed to `cancelled` with a portfolio reason and is never sent. Existing positions, close intents, timed exits, broker-attached SL/TP and reconciliation are never blocked by this gate.

Visible broker positions are identified only by known BrainTrade magic numbers for the bound symbol. A filled/partial intent is not double-counted after its corresponding brain-owned position becomes visible. Unresolved `dispatched`, `unknown`, `placed`, `filled` and `partial` open intents remain part of exposure until reconciliation. Stop risk uses the conservative larger broker tick value plus the configured round-trip commission estimate. If aggregate risk is enabled but a contributing position has no valid protective stop, tick economics are unavailable, or another required risk value is invalid, new entries fail closed rather than assuming zero risk.

Portfolio settings are persisted in the Core SQLite state and therefore participate in schema-12 application backup/restore. The separate gateway send journal remains outside rollback exactly as before. The API is `POST /v1/execution/portfolio` with `{enabled,max_positions,max_lots,max_risk_percent}` and is accepted only while global START is off. `GET /v1/execution` exposes the active limits and current aggregate exposure. The native Execution page now displays the current portfolio state and provides a stopped-only editor for all four portfolio settings; after saving, the page reloads the persisted Core values rather than trusting the local form state.

Broker deal profit, commission, swap and fee are recorded and deduplicated by ticket. Manual exits with magic zero are attributed by the known position identifier. Fees without a usable position ID cannot automatically be assigned to a brain. The calculator's commission is a round-trip estimate per full lot in account currency; actual results use broker-reported fees.

Normal full snapshots continue on a slower cadence, while Sniper quote arrival uses the native `OnTick`/`CopyTicks` bridge and automatically falls back to a 5 ms Python quote poll when the native bridge is absent or stale. These are transport/update cadences, not promised decision/order latencies. Account/history calls, analysis, network and broker work add time. Classic Sniper evaluates a live bid/ask breakout of the last six completed M1 bars with M5 agreement. Sniper Learner evaluates short tick impulses/rebounds, selects a configurable fixed pip target or four bounded Demo-only pip arms, and learns the selected policy/target from complete MT5 Demo closes. When coordinated by `system` (magic 410600), the real position remains system-owned, but the specialist receives a separately scoped learning reference to the same booked result; it does not create or double-count a broker position. Target and stop use broker points, with commission/exit slippage compensation in the target. The selected maximum cost fraction also applies to the actual Sniper broker policy; a cost-heavy entry remains WAIT. Broker-attached SL/TP can act independently of UI polling. Decision microseconds and queue/check/send milliseconds are measured on actual operations. The dashboard refresh interval is separate. This is not an HFT or tick-complete feed.

## Persistence and verification

Backup schema 12 includes configurations, broker intents/deals/observations, adaptive samples and portfolio-limit state. The separate durable gateway send journal is intentionally never rolled back with an application backup, so restoring an old Core database cannot resend an already journaled order. A restored/new Core starts STOPPED. Existing working databases migrate additively; sealed backups require the exact application version/schema.

`python scripts/check_execution.py` runs a real Core against a simulated MT5 object in isolated temporary storage. `scripts/check_backup_restore.py` additionally verifies that portfolio limits survive a staged restore/restart. `--exe BrainTrade.exe` checks the packaged Windows Core, including DPAPI IPC. These are not native broker acceptance. Latest recorded release CI evidence belongs in `docs/validation.json`; feature-branch CI must remain separate until a new release checkpoint is recorded.

# BRAINTRADE V26 — سجل إصلاحات الاستقرار المتتابعة

**تاريخ المراجعة:** 2026-11-04  
**الفرع:** `feature/v26-tp-stage-operator-arm-20261103`، PR #228 (Draft)
**حالة الإصدار:** كود تطويري وفحوص CI؛ ليست موافقة تداول Live أو ضمان تنفيذ Broker.

## P1-1 — منع تأخير القناص بسبب نسخ/تصدير كبير

`crates/runtime/src/lib.rs` يفرض `ensure_bulk_io_idle` على Backup / Brain Export-Import / قوائم النسخ وفحص الاستعادة / التعلم والتصدير الثقيل، عندما يكون START أو أوامر وسيط غير محسومة أو مراكز/أوامر موجودة في آخر Snapshot. تبقى مسارات STOP و`/v1/execution/*` والمصالحة من دون هذا القيد. **هذا احتواء لطلب البيانات البطيء وليس عزل threads حقيقياً**. العزل الكامل ومراجعة تنافس SQLite مهمة مستقلة لاحقة لا يجوز الادعاء بأنها مكتملة.

## P1-2 — مالك واحد لمنصة MT5

`gateway/managed_terminal.py` يشتق قفلاً من `terminal_info().data_path` ويمسك قفل ملف حصري عند نجاح `initialize`، ويحرره بعد انتهاء `cleanup_gateway`. يعمل على Windows عبر `msvcrt.locking` وعلى Linux عبر `fcntl` للاختبارات. يمنع مثيلين جديدين من BRAINTRADE من التداول من خلال نفس مجلد بيانات المنصة حتى إذا اختلفت مجلدات Core. ملف القفل في المجلد المؤقت لا يعني أن العملية ما زالت حية؛ الحكم للقفل الذي يحتفظ به النظام.

تمت إضافة اختبارات لنسختين بنفس `data_path`، ولنسختين بمجلدين منفصلين، واختبار ملكية بين عمليتي Python مستقلتين.

## P1-3 — منفذ Named Pipe فريد ومربوط بالجلسة

`gateway/sniper_native.py` ينشئ `\\.\pipe\BrainTradeSniperV1-<24hex>` لكل جلسة، ويكتب `sniper.pipe` في مجلد `MQL5/Files/BrainTrade` وبداخله token مطابق لـ`sniper.token`. إصدار EA **1.17** يقرأ الملف ويتحقق من تطابقهما وصيغة الاسم قبل فتح Pipe. تُحذف metadata عند نهاية الجلسة فقط إذا كانت تخص نفس token/pipe. يظل `InpPipeName` الثابت للتوافق مع Gateway قديم **عندما لا يوجد ملف sidecar فقط**.

**هام:** EA 1.15 أو أقدم لا تعرف `sniper.pipe`، ولذلك لا يمكن اعتماد `Native` عليها مع Gateway الجديد. استخدم EA 1.17 مترجمة من نفس نسخة المصدر؛ وإلا سيستخدم النظام fallback polling من دون الادعاء بوصول Native.

## P1-4 — تقليل حمل OnTick وإظهار زمن الحجب

داخل `mt5/BrainTradeSniperBridge.mq5`: `OnTick` يمرر دفعة محدودة `InpOnTickBatch=64` (حد 32..128)، وتستمر `OnTimer` باسترداد الدفعات المتبقية وفق الـcursor. تبقى `FileFlush` ضرورية لإيقاظ القارئ فوراً، مع تسجيل `Max FileFlush microseconds` و`Max OnTick microseconds` و`Slow OnTick count` لقياس التأخير، بدلاً من إزالة flush عشوائياً والتضحية بالزمن.

## P1-5 — قياسات HTTP المحلية وتشخيص Core

`gateway/mt5_gateway.py` يسجل `BRAINTRADE_LOCAL_LATENCY` كل 30 ثانية، مع p50/p95/p99 وMax لكل من `core_pulse_ms` و`gateway_cycle_ms` و`snapshot_ms`؛ مخزن مؤقت بحد 1,024 عينة لكل مسار، وبدون سعر أو token أو حساب. `crates/runtime/src/lib.rs` يسجل `CORE_SLOW_ROUTE` للطلب الذي يتجاوز 75ms بفئة آمنة فقط مرة كل 10 ثوانٍ. أزمنة HTTP هذه **لا تساوي زمن وصول الصفقة للوسيط أو تنفيذها**.

## P1-6 — توافق أخطاء HTTP في مسار Core المحلي

`gateway/transport.py` يعيد الآن أخطاء HTTP غير الناجحة من Core بصيغة `urllib.error.HTTPError` المتوافقة مع العميل القديم، مع إغلاق الاتصال ودون أي إعادة تلقائية للطلب. كان HTTP 400 يرجع `OSError` عامة، فلا تتعرف عليه `HvnResultOutbox` وتظل تكرر إيصال HVN مرفوضاً وتمنع الأبحاث الأخرى. يتعرف Outbox مجدداً على HTTP 400 ويُغلق الإيصال المرفوض، بينما تبقى 401 وأخطاء الاتصال غير محسومة ولا تتحول إلى إذن تداول. يوجد اختبار HTTP محلي فعلي لهذه الحالة. هذا إصلاح لتدفق الأبحاث وليس شهادة تنفيذ Broker.

## P1-7 — تخفيف طلبات Core أثناء خمول التيكات

`BrokerHistoryScheduler` كان يعيد طلب `/v1/execution/gateway` مع كل دورة Sniper (~5ms) عندما لا يحدث نبض Tick، حتى دون وجود عمل جديد. أضيف حد 50ms لدورة الفحص العادية وقت خمول التيكات، مع إبقاء نبضات الأسعار السريعة من دون تأخير إضافي، وفحص History الإلزامي كل 5 ثوان أثناء التدفق المستمر. هذا يقلل الحمل المتوقع دون أن يكون قياس أداء فعلياً على جهاز المستخدم. اختبار رجوع يحاكي 200 دورة في ثانية بدون Quote، واختبار الاستمرار في الفحص أثناء التدفق.

## P1-8A — عزل الحسابات البحثية البحتة عن حلقة Core

`crates/runtime/src/lib.rs` يرسل **أربع واجهات بحثية POST محددة** إلى عامل Rust منفصل أحادي التنفيذ بطابور محدود (واحدة تعمل + واحدة تنتظر): Lifecycle Replay وAdmission وExecution Bridge وDemo Deal Audit. كل واجهة تحسب على Body المرسل فقط، من دون Engine أو MT5 أو SQLite أو أوامر Broker، وبعد التحقق من صلاحية الطلب وحجمه. امتلاء الطابور أو توقف العامل ينتج HTTP 503 بدلاً من تراكم غير محدود. أخطاء الحساب غير السليمة ترجع HTTP 400 وPanic داخل العامل يرجع 500 من دون انهيار Core.

تبقى `/v1/execution/*` و`/v1/gateway/snapshot` وSTOP وShutdown وSnapshot والمصالحة بملكية حلقة Engine الحالية؛ لا تجري أي أوامر تداول في عامل الأبحاث. أضيف اختبار وحدات للـAllowlist واختبار HTTP تكاملي في `scripts/smoke_core.py` يتزامن فيه حساب بحثي بحجم 3000 حدث اصطناعي مع طلب حالة النظام، ويتأكد من عدم صدور أوامر MT5. هذا **عزل حسابات CPU المحددة فقط**، ولا يثبت فصل باقي الطلبات أو سلاسل SQLite.

### تحليل المخاطر المتبقية قبل P1-8B

- `Engine::tick` يستدعي Studio/News/Backtest/Evaluation على خيط الطلب نفسه حتى أثناء الاستقبال؛ يلزم قياس P95/P99 والتأكد من عدم تجاوز ميزانية نبضة القناص، ثم فصل صريح للخدمات ذات الحالة مع اختبارات الاستئناف والإيقاف.
- قاعدة `events.sqlite` بنمط WAL و`synchronous=FULL` يستخدمها Engine كاتصال مالك واحد. عملية `backup::create_named` تستعمل SQLite Backup API وتحقيق سلامة ومقارنة ملفات؛ لا ننقلها ببساطة إلى خيط ثان لأن قبول START أو تبديل الحساب أثناء نسخة غير مكتملة يخرق شرط STOP/Flat الحالي. يلزم عقدة حالة مستقلة وحجز نطاق النسخ، ثم فتح اتصال Read-Only أو Snapshot مستقل بمصالحة ذرّية قبل التطوير.
- نقل الأبحاث إلى خيط واحد يزيل انتظارها داخل طابور Core، **لكنه لا يلغي التنافس على CPU**، أو Block في قارئ HTTP الأساسي، أو تزامن أوامر Core. لا يوجد إثبات أداء على وسيط MT5 الفعلي بعد.

## P1-8B — توزيع صيانة Studio/News/Backtest/Evaluation

`Engine::tick` لم يعد يشغّل الخدمات الأربع في نفس فرصة صيانة الـ50ms. جدولة `MaintenanceRotation` تختار خدمة واحدة في كل فرصة متاحة مع استمرار تحديث حالة النظام ومراقبة Gateway قبل الصيانة، ويُسجّل `CORE_SLOW_MAINTENANCE` للخدمة التي تتجاوز 75ms (بدون أسماء حسابات أو محتوى أسرار). لا تتغير مسارات `/v1/execution/*` أو نتيجة Ledger/Deals، ولا يجرى تشغيل العمال البحثيين بملكية مستقلة لـSQLite.

`news::Service::tick` أصبح يعالج/يحفظ تحديث مصدر RSS واحداً كحد أقصى لكل دورة خبر، بدلاً من تشغيل ثلاث معاملات حفظ متتابعة فور وصول دفعة كاملة؛ التحديثات الأخرى تبقى في القناة للدورات اللاحقة. أضيف اختبار Rust لدورات الصيانة المنتظمة، واختبار SQLite حقيقي يتأكد من تقدّم حفظ 3 تحديثات على 3 دورات من دون فقد بيانات.

**حدود الإثبات:** فصل وقت الصيانة يخفض احتمال تجمع أعمال ثقيلة متتابعة؛ لكنه لا يزيل انتظار Core أثناء معاملة واحدة كبيرة. بسبب `recv_timeout(250ms)` قد يقل تردد المهام غير الحرجة أثناء خمول كل طلبات HTTP؛ هذا مقبول للأخبار والتقارير، لكنه يتطلب اختبار زمن قبول الأوامر والحمل على جهاز Windows. لا يُقدَّم هذا كدليل تحسن P99 قبل وجود Benchmarks.

## P1-8C — كتابة مشاهدات الأخبار بمعاملة SQLite ذرّية ومحددة المصدر

`news::Service::persist_sources` يربط حفظ `news_cache` وإلحاق مشاهدات `news_observed_events` ضمن معاملة SQLite واحدة؛ عند فشل التحقق من أحد عناصر المصدر، تتراجع المعاملة كلها ولا تُترك حالة Cache محفوظة مع Replay ناقصة. أثناء تحديث مصدر RSS دوري، يعاد تحديث مشاهدات ذلك المصدر وحده، ولا تعاد كتابة مشاهدات المصادر الأخرى في كل مرة. تبقى عملية حفظ إعدادات المصادر الكلية تستخدم المسار الشامل.

أضيف اختبار انحدار في Rust يتحقق من تراجع Cache ومشاهدات التاريخ معاً عند وصول URL غير موثوق. هذا تحسين اتساق وكلفة كتابة، ولا يفصل Connection عن خيط Core ولا يؤكد أرقام latency على MT5/Windows.

## P1-8D1 — تأجيل حفظ نتائج Backtest/Evaluation الضخمة أثناء تعرّض الوسيط

تحليل الكود كشف أن `backtest::Service::tick` و`evaluation/core::Service::tick` يحفظان نتائج من عمال خارجية على اتصال SQLite الخاص بـCore. على وجه الخصوص قد تتضمن نتيجة Backtest History JSON كبيراً؛ كان حفظه يجري فور اكتمال العامل، حتى لو صار `START` فعّالاً أو كانت هناك أوامر/مراكز وسيط لم تُغلق.

في `Engine::tick` أضيف `historical_result_persistence_allowed` قبل تشغيل صيانة هاتين الخدمتين: يرفض معالجة نتائج الدراسة عندما يكون START فعّالاً، أو عند وجود مراكز/أوامر معلقة في آخر Snapshot، أو عند وجود أمر وسيط غير محسوم في دفتر التنفيذ. فشل الاستعلام عن حالة الدفتر يُعامل كوجود خطر، لا كسجل فارغ. لا يُسحب Completion من قناة العامل وقت التأجيل؛ يتم التعامل معه بعد STOP وتسوية المراكز/الأوامر، وتظل أوامر التنفيذ/STOP والمصالحة خارج هذا القيد. اختبارات Rust تغطي انتقالات START والمراكز/الأوامر والتسوية.

**المقايضة المعروفة:** هذا احتواء لعمليات حفظ ضخمة في Core، وليس Writer Thread مستقلاً. قد يبقى التقرير المحسوب في حالة Running إلى أن يصبح الحساب بلا انكشاف؛ لا يجوز عرض النتيجة على أنها محفوظة قبل Commit. استُخرج فحص مهلة جلب تاريخ Backtest إلى `check_loading_timeout`، ويستمر تنفيذه في صيانة Core حتى أثناء تأجيل كتابة التقرير. اختبارات Rust تغطي انتهاء مهلة التحميل بهذا المسار المستقل. جلب التاريخ الجديد لا يُسمح به أصلاً أثناء START.

## ما لم يُحل نهائياً

- `engine.tick` وبقية `engine.route` ونسخ SQLite لا تزال مشتركة في خيط Core؛ جرى عزل أربع وظائف بحثية حسابية فقط، ويظل فصل النسخ/SQLite ومعاملاتها مطلوباً قبل إزالة Head-of-Line بالكامل.
- `FileFlush` لا تزال عملية مزامنة داخل OnTick؛ تتطلب قياسات على جهاز المستخدم ثم قراراً بخصوص transport مختلف أو نقل النقل إلى Worker رسمي موثوق.
- يلزم اختبار MT5 حقيقي: تبديل الحساب أثناء STOP، وصول BT2/Heartbeat، فصل EA والإنترنت، فشل المرسل ثم المصالحة بدون تكرار `order_send`، وتقرير p95/p99 وقت Broker ACK/Deal مع خصائص وسيط المستخدم.
- نتائج CI قد تختلف بين commit وآخر؛ تُعتمد فقط الحالة المكتملة على آخر HEAD. لا دمج لـmain قبل الفحوص والقبول العملي.

**قاعدة الإصدار:** لا تحديث قديم باسم أحدث؛ ما لم تُفحص الحزمة ضد نفس SHA وتضم EA 1.17 وPython Gateway الجديد، لا توصف بأنها تحتوي هذه الإصلاحات.

# BRAINTRADE V4 — V26 | قبول التنفيذ الجزئي الحقيقي TP1 على Windows / MT5

**الوثيقة:** بروتوكول قبول يُنفَّذ أمام منصة MT5، وليس شهادة نجاح أو نتائج تداول حقيقية.

**مهم:** كل اختبارات CI والمحاكاة الآلية لا تثبت أن الوسيط نفّذ صفقة بالفعل. يبقى `BROKER_DEMO_ROUNDTRIP` و`BROKER_LIVE_ROUNDTRIP` بحالة **NOT TESTED** إلى أن تُجمَع أدلة MT5 على الحساب الذي يختاره المشغّل. لا يُعتمد دمج V26 في `main` بسبب نجاح CI وحده.

## 1. ما الذي يجب أن نراه؟

الهدف هو صفقة **موجودة مسبقاً**، مملوكة لـ BrainTrade على رمز الذهب المختار. يجب إثبات سلسلة البيانات والأوامر:

```text
STOP + حساب MT5 محدد ومتصّل + مركز Hedging مطابق
  -> خطة TP1 / TP2 / TP3 محفوظة وأسعارها على شبكة Tick
  -> موافقة التحضير (preparation_only)
  -> موافقة التداول المستقبلية (ليست إذن إرسال)
  -> تسليح التنفيذ لمركز واحد (مدة 15 دقيقة)
  -> START + Tick حديث يعبر هدف TP1
  -> Core stage_held (أمر محجوز) + سجل تدقيق
  -> Core queued + استهلاك حالة تسليح TP1 إلى consumed في نفس معاملة SQLite مع الإطلاق وسجل التدقيق
  -> Core dispatched + فحص جديد عند Gateway polling
  -> Gateway order_check + فحص السعر والحجم والمركز
  -> Core /authorize قبل وبعد كتابة دفتر الإرسال
  -> MT5 order_send لمرة واحدة كحد أقصى
  -> ACK/placed/unknown (ليس إثبات Fill)
  -> تاريخ MT5: Order + Deal tickets + تكاليف فعلية
  -> Core: broker_history_sync + broker_deals
  -> Snapshot مستقل: الحجم المتبقي على المركز الأصلي
  -> partial_exit_stage_settlements: historical_stage_sealed
```

إذا فشلت حلقة واحدة، تبقى النتيجة **غير مثبتة**. لا يُحتسب Fill اعتماداً على `retcode=10009` أو على تغيّر السعر أو على الربح العائم وحده.

## 2. تجهيز بيئة الفحص

1. استعمل **نفس Commit SHA** في شفرة Core وGateway وواجهة Windows وEA، ولا تخلط ملفات V25 وV26. وثّق رقم الإصدار والـSHA والتجزئة لكل حزمة؛ اختبارات GitHub لا تعني تشغيل ملف ZIP على حاسوبك.
2. افتح MT5 وتحقق من الاتصال واسم الخادم ورقم الحساب وعملته واسم رمز الذهب تماماً (قد يختلف مثل `XAUUSD` أو `XAUUSDm`). تحقق أن الحساب **Hedging**؛ مسار TP المرحلي الحالي لا يدعم Netting.
3. اختر **Demo أو Live بنفسك** من واجهة الحساب، وتحقق من أن `account_trade_mode` يطابق الاختيار. عند Live أدخل رقم الحساب الحقيقي كاملاً للتأكيد. لا يفترض النظام أن كل حساب Demo.
4. تحقق من ربط Gateway، وصول Tick بتوقيت متزايد وحديث، وظهور المركز الفعلي وحجمه واتجاهه ومُعرّفه وTicket. إذا بقي `BrainTradeSniperBridge` في WAITING أو لم تتحدّث الأسعار، **لا تختبر الإرسال**؛ عالج الربط أولاً.
5. استخدم STOP وراجع سجل الأوامر المفتوحة أو غير المحسومة. لا تختبر متغيرات العمولة/السبريد أو تغيّر الحساب أثناء إرسال سابق غير محسوم.
6. تحقق من `volume_min` و`volume_step` و`tick_size` و`volume_max` كما يبلّغ عنها الوسيط. مثال حسابي **فقط**: مركز 0.10 لوت مع min/step يساويان 0.01 يوزَّع TP1=0.05، TP2=0.03، TP3=0.02. مركز 0.01 قد لا يقبل 3 إغلاقات مستقلة وفق قيود العقد؛ لا يغيّر Core حجم اللوت خفية لإنجاح الاختبار.
7. احتفظ بنسخة من قواعد البيانات والسجلات **من دون كلمات المرور أو Token تلغرام** قبل البدء، وتأكد من وجود مساحة كتابة كافية.

## 3. اختبار TP1 الأساسي

1. اختر المركز الأصلي والرمز والحساب، ثم احفظ 3 مستويات TP مرتبة في اتجاه الربح وعلى شبكة Tick. تحقَّق من عدم تداخل TP الوسيط الأصلي مع مستويات الإغلاق الجزئي.
2. عند STOP احفظ **موافقة التحضير**، ثم **موافقة تداول TP1 المستقبلية**، ثم اضغط **تسليح تنفيذ TP1 الحقيقي** لهذا المركز وحده. التسليح ينتهي بعد 15 دقيقة؛ لا تفترض تجديده تلقائياً.
3. اضغط START وأبقِ الحساب والرمز مطابقين. راقب حالات `stage_held` ثم `queued` ثم `dispatched` عند وصول سعر قابل للتنفيذ، ولا تعتبر أي حالة منها نجاحاً مالياً.
4. تحقق من سجل Gateway: يجب أن يختار نفس `command_id` ونفس `tp_stage_plan_id` وTicket وأن يُنشئ **Send journal** دائماً قبل `order_send`. لا تُنفّذ أي عملية إرسال ثانية بنفس الأمر.
5. تحقق من MT5 من **History / Deals**، وليس من سجل واجهة BrainTrade وحده: رقم Order الإغلاق، أرقام Deal، `position_id`، الحجم المغلق الفعلي، السعر، `profit` و`commission` و`swap` و`fee` إن كانت متاحة.
6. بعد تحديث بيانات المركز الكاملة في MT5، تأكد من أن `partial_exit_stage_settlements` صار `historical_stage_sealed` فقط عند تطابق مجموع أحجام Deal مع TP1 وبقاء حجم المركز المتوقع؛ خلاف ذلك النتيجة `unsettled` أو `sealed_evidence_needs_review`.
7. قارن الربح المحجوز المعروض مع **مجموع حقول الـDeals المثبتة**. هذا مبلغ مرحلي، وقد لا يساوي صافي دورة الدخول/الخروج كلها إذا كانت عمولة الدخول في Deal مستقل.

## 4. اختبارات الانقطاع والإلغاء — لا تُجرى بالتزامن مع حساب Live ذي أموال معرضة للخطر

- **STOP قبل الإرسال:** يجب أن يمنع التفويض التالي. إذا صار `queued` ولم يبدأ الإرسال، يفترض أن يرفض Core الإذن. إذا كان الإرسال قد حدث، فلا تعتبر STOP أمراً بإلغاء صفقة عند الوسيط.
- **إلغاء التسليح بعد إطلاق الأمر للطابور:** يتحول التسليح إلى `consumed` عند الإطلاق الذري إلى الطابور. عند STOP يجب السماح بتحويله إلى `disarmed`؛ وهذا يمنع تفويض إرسال لاحق، لكنه لا يسحب أمراً سبق وصوله إلى الوسيط. لا تفسّر `consumed` بحد ذاته كـDeal أو Fill.
- **انقطاع Gateway بعد كتابة Send journal:** بعد إعادة التشغيل، يراجع Gateway تاريخ MT5 لنفس الأمر ولا ينشئ `order_send` ثانياً.
- **نتيجة `unknown` أو `placed`:** لا تُحوّلها إلى `filled` أو `cancelled` بالتخمين. اطلب سجلات MT5 الدقيقة أو احجب النتيجة حتى المصالحة.
- **تغيّر `position_identifier` أو Ticket أو الحجم أو سعر Bid/Ask أو حساب Demo/Live:** يجب أن يرفض الإرسال المرحلي من دون تغيير أمر الإغلاق إلى إغلاق كامل.
- **فشل SQLite وقت حفظ الأمر أو إذن إطلاقه:** يجب أن تتراجع **معاً** حالة `broker_commands` والإذن `partial_exit_tp1_arms` وسجل `partial_exit_tp1_releases` والحدث عند أي فشل حفظ، بما فيه فشل آخر خطوة Event Audit. لا يجوز أن يبقى `queued` بلا إذن `consumed` أو العكس. اختبارات حقن الفشل الآلية لا تعوّض فحص الاستعادة على Windows.

**حالة تحتاج علاجاً قبل اعتماد الإصدار:** إذا نشأ `stage_held` ثم انتهت صلاحيته قبل إطلاقه، يبقى محفوظاً وغير قابل للإرسال لحماية التكرار. يعرض Core الآن `manual_replan_required=true` و`automatic_requeue_allowed=false`، والواجهة تطلب مراجعة تاريخ MT5 والـDeals. لا يتوفر حتى الآن مسار آمن معتمد لإعادة تخطيط TP1 على نفس المركز؛ لذلك اعتبرها `BLOCKED_OPERATOR_REVIEW` لا نجاحاً ولا إعادة محاولة تلقائية.

## 5. مصفوفة القبول

| البند | الدليل المطلوب | الحالة الافتراضية |
|---|---|---|
| Windows Native | نجاح Build/Portable واختبار EXE على Windows | NOT TESTED حتى التشغيل الفعلي |
| ربط MT5 وEA | اتصال حقيقي وTick ومركز وحساب صحيح | NOT TESTED |
| اختيار Demo / Live | هوية Target ومركز وحساب متطابق | NOT TESTED |
| TP1 إرسال مرة واحدة | Core command + Gateway send journal + order_send واحد | NOT TESTED |
| نجاح الإغلاق | Order + Deal IDs + مجموع حجم إغلاق مطابق | NOT TESTED |
| صافي التكاليف | Deal profit + commission + swap + fee | NOT TESTED |
| إثبات حجم المركز المتبقي | Snapshot مستقل و`historical_stage_sealed` | NOT TESTED |
| STOP / restart / disconnect | منع إعادة الإرسال وعدم اختلاق نتيجة | NOT TESTED |
| إعادة تخطيط TP1 بعد تعثر `stage_held` | مسار تدقيق وإلغاء وإعادة موافقة بلا إرسال مكرر | BLOCKED |
| تنفيذ TP2 وTP3 تلقائياً | اعتماد Deal المرحلة السابقة ثم أمر ومصالحة جديدة | NOT IMPLEMENTED |
| BE آلي بعد TP1 | تعديل SL عبر MT5 مع نتيجة وسيط موثقة | NOT IMPLEMENTED |

**معيار إصدار قابل للدمج:** جميع فحوص CI المطلوبة خضراء على SHA واحد، فحص Windows حقيقي، نتائج MT5 المقبولة موثقة مع عدم تكرار، وحل الحالات المعروفة المذكورة أعلاه أو تضييق نطاق إصدار V26 بوضوح دون ادعاء إكمال TP2/TP3/BE.

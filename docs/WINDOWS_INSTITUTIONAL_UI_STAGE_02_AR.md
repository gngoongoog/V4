# UI-02 — توحيد الثيمات وحفظ مظهر واجهة Windows الأصلية

هذه المرحلة مكملة لواجهة BRAINTRADE V4 المبنية **داخل نفس تطبيق Rust/Slint** في PR #116. لا يوجد Web أو React أو تطبيق مختلف.

## الأشياء المنفذة

- توحيد ألوان النصوص والحواجز، وتقسيم ست بطاقات KPI إلى صفين واضحين بدل قص البطاقة الأخيرة عند عرض 1120px، على صفحات القناص والعقول والتكاليف وسجل الصفقات والتحليلات والمخاطرة والتعلم. الثيم الأبيض يعتمد نصوصاً داكنة واضحة، وثيما الدارك والدخاني يحتفظان بالتباين المناسب.
- الصفحة المنفصلة لتحليل الارتباط أصبحت تستقبل الثيم الحالي بدل أن تبقى مظلمة عند اختيار الأبيض.
- اختيار الدارك/الأبيض/الدخاني وطي القائمة الجانبية يُحفظ محلياً في `ui-appearance.json` تحت `braintrade_runtime::data_dir()`. الملف خاص بالواجهة فقط، ولا يحتوي أسرار MT5 أو Telegram أو إعدادات التداول. تُرفض قيم الثيم غير المعروفة وتعود الواجهة للافتراضي.
- أظهر اختبار الصور الأصلي أن `ColorScheme.light` مع Slint 1.16 يجعل نص أزرار Fluent فاتحاً جداً على خلفية بيضاء في فاحص الرسم. لهذا ثبّتنا نمط Windows أصلي `fluent-dark` في `crates/desktop/build.rs` لضمان أزرار داكنة بنص واضح فوق المساحات البيضاء؛ ونستخدم نفس الودجت الأصلي مع دعم لوحة المفاتيح، وتتحول بقية أسطح الواجهة والنصوص إلى الثيم المختار. هذا قرار وظيفي لتجنّب اختفاء أسماء الأزرار. تغيير الثيم لا يغيّر وضع Demo/Live أو سياسة المخاطر أو العقول أو أوامر التداول.
- فحص `--render-check` يمر على **جميع الصفحات الـ22** بالألوان الثلاثة وبحجمَي نافذة، مع الإبقاء على ملفات لقطة الدارك التاريخية وحفظ لقطات إضافية تمثيلية لسبع صفحات حساسة بالثيم الأبيض والدخاني. يهدف ذلك إلى اكتشاف فشل Slint والاختفاء والانقطاعات، لكنه لا يضمن تجريب كل زر بالماوس أو توافق كل شاشة Windows فعلية.
- اختبار Static contract يرفض أي زر Slint بلا callback ويربط `save-appearance` بمعالج Rust، ويتحقق أن لوحة التعلم لا تضع نسبة نجاح متخيلة عند غياب البيانات.

## ما بقي للوصول للجاهزية

المراحل التالية تحتاج تنقيح الطباعة والمسافات في كل صفحة مع صور المرجع وعمل فحص screenshot review يدوياً على جهاز Windows، ومراجعة مسؤولية كل زر خاصة الإغلاق الحقيقي والتأكيدات وإدارة المخاطر، واختبار شارت السوق في جلسة MT5 Demo. لم نثبت بعد المطابقة البصرية التامة، ولا دقة حساب Broker latency أو الإحصائيات غير المدعومة؛ حقولها يجب أن تظل «غير متاحة». لا يمكن اعتبار «100%» وصفاً صادقاً بغير اختبار قبول نهائي على Windows وعلى حساب Demo.

## قواعد الدمج

PR تابع #116 ويُدمج بعد نجاح فحوص Windows وResearch وLinux على الـ SHA النهائي، وبعد دمج الفرع الأم.
